# Конфигурация обнаружения аномалий

* Explanation
* 7-min read
* Updated on Jul 27, 2026

Конфигурация обнаружения аномалий опирается на несколько компонентов:

* Источник данных, временной ряд, который оценивается. Например, конкретная метрика.
* Тип анализатора и параметры: как именно оцениваются данные.
* Скользящее окно: период, за который оцениваются данные.
* Шаблон события: какой тип шаблона срабатывает в рамках конфигурации.

После настройки и активации конфигурация отслеживает данные и инициирует событие при выполнении условий. Чтобы убедиться, что конфигурация работает корректно и оповещает о нужных событиях, можно предварительно просмотреть результаты её работы:

* Preview метрического события наглядно отражает поведение события. Можно корректировать настройки и наблюдать, как они влияют на конфигурацию.

## Источник данных

Источник данных предоставляет временной ряд, который оценивается Davis:

* Метрика определяет временной ряд. Это может быть одна метрика, заданная ключом метрики, или [metric expression](/managed/dynatrace-api/environment-api/metric-v2/metric-expressions "Use metric expressions to apply arithmetic operations in a data points query via the Metrics API v2.").

Если данные поступают с задержкой, нужно учесть её в конфигурации через параметр **Query offset**. Значение указывается в минутах.

## Тип анализатора и параметры

Параметры анализатора определяют, как Davis оценивает данные, полученные из источника. Конкретный набор параметров зависит от типа анализа:

* [Auto-adaptive threshold](/managed/dynatrace-intelligence/anomaly-detection/auto-adaptive-threshold "How Dynatrace adapts thresholds for multiple entities within the scope of an anomaly detection configuration."): Dynatrace рассчитывает порог автоматически и динамически адаптирует его к поведению данных.
* [Seasonal baseline](/managed/dynatrace-intelligence/ai-models/seasonal-baseline "How Davis suggests Seasonal baseline thresholds for a scope of entities."): Dynatrace формирует полосу доверия для данных с сезонными паттернами.
* [Static threshold](/managed/dynatrace-intelligence/anomaly-detection/static-thresholds "When to use a static threshold for your anomaly detection."): порог, который не меняется со временем.

| Parameter | Description |
| --- | --- |
| Number of signal fluctuations | Auto-adaptive threshold состоит из двух компонентов: базовой линии и флуктуации сигнала. Этот параметр определяет, сколько раз флуктуация сигнала прибавляется к базовой линии. Подробнее: [Threshold calculation](/managed/dynatrace-intelligence/anomaly-detection/auto-adaptive-threshold#calculation "How Dynatrace adapts thresholds for multiple entities within the scope of an anomaly detection configuration."). |
| Threshold | Этот параметр задаёт значение статического порога и, при необходимости, его единицу измерения. Выберите **Suggest values**, чтобы использовать значение, рассчитанное Davis на основе предыдущих данных. |
| Tolerance | Этот параметр определяет [tolerance](/managed/dynatrace-intelligence/ai-models/seasonal-baseline#parameters "How Davis suggests Seasonal baseline thresholds for a scope of entities.") сезонной модели. Чем выше tolerance, тем шире полоса доверия и тем меньше срабатываний. |
| Alert condition | Этот параметр определяет условие срабатывания события: метрика выше, ниже или за пределами порога. |
| Missing data alert | Этот параметр определяет, активен ли алерт на отсутствующие данные для конфигурации. Если активен, он объединяется с условием по порогу через логику **OR**. Параметр находится в разделе **Advanced properties** конфигурации. |

## Missing data alert

Dynatrace позволяет настроить алерт на отсутствие данных в метрике или запросе DQL. Если алерт активен, Dynatrace регулярно проверяет, содержит ли скользящее окно конфигурации обнаружения аномалий какие-либо измерения. Например, если скользящее окно задано как **3 violating samples during any 5 minutes**, Dynatrace инициирует алерт при отсутствии данных в течение 3 минут.

Условие отсутствия данных и условие по порогу объединяются через логику **OR**.

Рекомендуется отключать алерт на отсутствие данных для разреженных потоков данных, где измерения не ожидаются через регулярные интервалы: это позволит избежать шторма алертов.

Для данных, которые ожидаемо поступают с задержкой (например, метрики облачных интеграций с задержкой 5 минут), нужно использовать длинные скользящие окна, перекрывающие задержку. При задержке 5 минут скользящее окно должно составлять не менее 10 минут.

Плейсхолдер `{missing_data_samples}` в описании события подставляет количество минут, в течение которых данные не поступали.

## Скользящее окно

Скользящее окно конфигурации обнаружения аномалий определяет, сколько одноминутных сэмплов должны нарушить порог за определённый период. Когда заданное количество нарушений достигнуто, Dynatrace поднимает событие. Цель: избежать избыточных оповещений при единичных нарушениях, когда каждое измерение, выходящее за порог, инициирует событие.

Событие остаётся открытым до тех пор, пока метрика не вернётся в пределы порога на определённое количество одноминутных сэмплов в рамках того же скользящего окна, после чего Dynatrace закрывает событие. Удержание события открытым помогает избежать избыточного оповещения: новые нарушения порога добавляются к существующей проблеме, а не создают новую.

Настройки скользящего окна находятся в разделе **Advanced properties** конфигурации. По умолчанию:

* Для поднятия события нужно, чтобы три из пяти одноминутных сэмплов нарушили порог.
* Для закрытия события нужно пять одноминутных сэмплов в пределах нормы.

Для каждого из трёх типов анализатора можно задать скользящее окно продолжительностью до 60 минут.

Рассмотрим пример со статическим порогом использования CPU на уровне 90%.

![Объяснение скользящего окна и де-алертинга](https://dt-cdn.net/images/sliding-window-example-2026-39b1adf7bb.png)

Объяснение скользящего окна и де-алертинга

Анализ события начинается с первого нарушающего сэмпла в скользящем окне. Как только количество нарушающих сэмплов достигает заданного порога, анализ события прекращается и поднимается проблема. Несмотря на то что анализ события остановлен, само событие остаётся открытым до выполнения критериев де-алертинга:

* Количество нарушающих сэмплов должно быть ниже порогового числа для поднятия проблемы.
* Количество «нормальных» сэмплов должно быть больше или равно количеству сэмплов де-алертинга.

**Оба** условия должны быть выполнены для закрытия события.

Значения по умолчанию (3 нарушающих сэмпла в скользящем окне из 5 для срабатывания проблемы, 5 сэмплов де-алертинга для закрытия) подходят для большинства конфигураций. Однако их может потребоваться скорректировать (например, из-за шума в измерениях).

## Шаблон события

Шаблон события определяет характеристики события, которое срабатывает при нарушении порога. Необходимо указать как минимум имя и тип события.

* Для быстрого понимания события имя должно быть коротким и читаемым описанием ситуации, например `High network activity` или `CPU saturation`.
* Имя может содержать плейсхолдеры, например `{threshold}` или `{alert_condition}`. В реальном событии плейсхолдеры заменяются фактическими значениями. Чтобы посмотреть доступные плейсхолдеры, введите `{` в поле ввода. Доступны следующие плейсхолдеры:

  + `{alert_condition}` - условие алерта (выше/ниже порога).

    Если для **Alert condition** задано значение `Alert if the metric is outside`, плейсхолдеры `{threshold}`, `{severity}` и `{baseline}` будут недоступны.
  + `{baseline}` - нарушенное значение базовой линии.
  + `{dims}` - список всех измерений (и их значений) метрики, нарушившей порог. Можно также указать конкретное измерение: `{dims:dt.entity.<entity>}`. Чтобы получить список доступных измерений для метрики, нужно запросить её через запрос GET metric descriptor.
  + `{entityname}` - имя затронутой сущности.
  + `{metricname}` - имя метрики, нарушившей порог.
  + `{missing_data_samples}` - количество сэмплов с отсутствующими данными. Доступно только при включённом алерте на отсутствие данных.

    `{missing_data_samples}` в описании события

    Рекомендуется включать плейсхолдер `{missing_data_samples}` в описание события, чтобы видеть, поднята ли проблема из-за отсутствия данных или из-за нарушений порога.
  + `{severity}` - severity события.
  + `{threshold}` - нарушенное значение порога.

Избегайте раскрытия PII через плейсхолдеры алертов

Плейсхолдеры, например `{dims}`, напрямую подставляют значения измерений из результата запроса DQL в заголовок и описание события. Если запрос возвращает поля с персональными данными (PII), например имена пользователей, адреса электронной почты или идентификаторы клиентов, эти значения становятся частью текста события.

Поскольку события могут пересылаться в сторонние каналы уведомлений, например в интеграции с электронной почтой или Slack, настоятельно рекомендуется не использовать плейсхолдеры, ссылающиеся на поля с PII. Чтобы предотвратить случайное раскрытие PII, нужно исключить чувствительные поля из запроса DQL до их добавления в шаблон события. Для этого можно добавить к запросу команды `fieldsRemove` или `fieldsKeep`.

Дополнительные параметры можно указать в виде пар «ключ-значение». Список возможных свойств события: [Semantic Dictionary](/managed/upgrade/unavailable-in-managed "Your selection is unavailable in Dynatrace Managed.").
